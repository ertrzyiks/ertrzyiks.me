# Procedural pixel art with a hand-rolled atlas packer, replacing TexturePacker

Terrain and unit art for the visual refresh is generated by an in-repo script
(palette + pixel-grid drawing, raw PNG encoding via `zlib`) rather than
hand-drawn/commissioned art or an AI image-generation service, and that same
script assembles the TexturePacker-format atlas PNG + JSON manifest itself
instead of shelling out to the TexturePacker CLI — which isn't installed in
the environment this work was authored in and is a paid proprietary tool.
`preload.ts`/`Spritesheet`-consuming code is unaffected: the generator's
output matches the existing atlas format exactly.

## Considered Options

- Hand-authored/commissioned pixel art, wired in by hand — rejected: no
  artist in the loop for this pass, and the goal was a reproducible source of
  truth that can be tweaked by editing code, not image files.
- AI image-generation service — rejected: no image-gen tool is available in
  this environment, and reliable strict-grid pixel output (fixed palette,
  fixed dimensions, no anti-aliasing) is hard to guarantee from a generative
  model without heavy post-processing.
- Keep using the external TexturePacker CLI for packing, generate art some
  other way — rejected: not installed here, and worth removing as a
  proprietary external dependency for something as simple as multi-sprite
  packing.

## Consequences

- Future art changes are made by editing the generator script's palettes and
  pixel grids, not by opening an image editor.
- If richer/hand-painted art is wanted later, this decision would need to be
  revisited or superseded — the generator's output is a deliberate
  placeholder replacement, not assumed to be final-forever art.
