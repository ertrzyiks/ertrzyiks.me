# Implementation Plan

Progress tracking for this project lives in **GitHub Issues**, not here — see the "Wayfinder: Make the game fully playable (Stages 1-3)" epic (#141) and its linked sub-issues for what's done and what's left. Check `specs/*` for behavioral contracts.

This file now holds only durable technical knowledge that doesn't belong in an issue tracker: architectural decisions, gotchas, and open design questions future work needs to know about.

## Architectural notes for future work

- **`allUnits` is how a behavior sees enemies.** The per-player proxy exposes `state.allUnits` (full roster) plus `state.units` (this player only). `FleeBehavior` and `SeekerBehavior` both read `allUnits` and take an explicit owner-id list (`fleeFrom`/`huntFor`) rather than "everyone who isn't me". Raw (unproxied) state leaves `allUnits` undefined, so always `allUnits ?? units`.
- **Un-attackable = no `Damageable` mixin.** The Wanderer is made un-targetable purely by lacking `Damageable` (`isDamageable` false). Both attack paths gate on it: `PackBehavior.tryAttack` filters `isDamageable`, and `player_store` Attack rejects a non-damageable target before spending the charge. Any future "cannot be attacked" unit should just omit `Damageable`.
- **SPEC INCONSISTENCY (specs 06 vs 09) — unresolved, needs a human decision.** Spec 06 says a wolf "attacks any adjacent non-wolf unit at the end of its move" (would include Whirley), but spec 09 says "The wolves do not target Whirley." The current implementation follows spec 06 (`PackBehavior.tryAttack` bites any adjacent damageable non-wolf — it WILL bite Whirley; it won't bite the non-damageable Wanderer). This contradicts spec 09's "walk past the pack / fight through if cornered" framing. Two ways to resolve it: (a) wolves never target Whirley (pack becomes a pure ambient hazard — makes the stage trivial), or (b) accept spec 09's line as loose flavor and keep spec-06 behavior, tightening spec 09's wording instead. Do NOT silently pick one without confirming the intended difficulty with the project owner.
- **Occupancy + zero-budget are enforced in the reducer (single source of truth).** `createMoveContext` still keeps AI off occupied tiles pre-dispatch, but the `Move` reducer independently rejects (a) a move by a `Movable` unit with `!canMove()` and (b) a move onto a hex held by any other unit — covering every mover (human + AI). Bounds and adjacency remain caller-enforced (the reducer has no tile/click geometry).
- **Win/lose is evaluated in `Game`, not the reducer.** The reducer is pure and knows neither goal sections nor which player is human, so end conditions live in `core/conditions/` as pure predicates and `Game.onWorldUpdate` evaluates them after each `Move`/`TakeDamage`, dispatching `GameEnd`. `GameEnd` sets `state.outcome`, which the reducer then uses to reject all further gameplay (terminal state).
- **Narrative pauses via the serial Observable, not a flag.** A beat is shown by a world-observable subscriber (`MainWorld.onNarrativeUpdate`) that withholds `done()` until the dialog queue drains. Because the `Observable` publishes items serially (the next item waits on `Promise.all` of every subscriber's `done`), this freezes everything — including a `GameEnd` the Game already queued behind a winning `Move`. Each stage's narrative script is a plain factory function (see `main/narrative/stage1.ts`/`stage2.ts`/`stage3.ts`) passed to a fresh `NarrativeEngine`. **Stage reset must call `narrative.reset()`** so beats replay on reload — already wired for the same-stage reload case (`MainWorld.reloadCurrentStage`).
- **One step per unit per turn.** Both `Explorer` and the AI behaviors dispatch a single Move per unit even when the unit has >1 movement point. Matches spec wording ("moves one step") but means multi-point budgets are underused.
- **`Scenario` is `StageDefinition`-driven, not hard-coded per stage.** `main/scenario.ts`'s `Scenario` takes a `StageDefinition` (player, spawns, an ordered list of enemy factions each with their own AI behavior, win section) instead of Stage-1-specific fields — `main/stages/stage1.ts`/`stage2.ts`/`stage3.ts` are factory functions each producing one. `Scenario.reload(definition)` reuses the same instance to reset+respawn (built for same-stage reload on lose; the underlying `Observable` has no unsubscribe, so a second `Scenario` instance would double-drive every future turn). `StageDefinition` deliberately excludes the board and narrative script — board is chosen one layer up at `new Game(board)` construction, narrative is wired separately by `MainWorld` — neither is consumed by `Scenario` itself.
- **The `Reset` game event exists but is board-preserving only.** `GameEventType.Reset` clears every per-playthrough field (players, units, turn, currentPlayer, revealedTiles, outcome — see `core/world_defaults.ts`'s `EMPTY_PLAYTHROUGH_STATE`, shared with `World`'s constructor) but keeps the board/tiles/dimensions untouched. Fine for reloading the *same* stage. Switching to a stage with a genuinely different board (e.g. Stage 1 → Stage 2) needs a new `Game`/`World` constructed from the new board, plus the Pixi renderer (terrain/fog/viewport, not just unit sprites) rebuilt around it — `GameViewport.resize(w, h, worldW, worldH)` and `TerrainTiles.clear()` already exist as reusable primitives for that, but nothing wires them together yet.
- **No Pixi testing convention exists in this repo.** `shared/game_world.ts` and `main/game_world.ts` (the Pixi rendering layer) have zero test coverage and no test harness to extend — verify changes there via `tsc --noEmit`, a full `astro check && astro build`, and careful code review instead. Headless browser verification (Playwright) is currently blocked by this sandbox's network policy (`cdn.playwright.dev` denied) — if that's ever unblocked, it would meaningfully de-risk future Pixi-touching work.
- **Coupling risk: `EnemyRoster.turnEventName` is a bare string.** Each stage definition's enemy factions declare a `turnEventName` (e.g. `"banditTurn"`) that `Scenario` emits and `MainWorld` is expected to listen for to show turn-specific UI. Nothing ties the two together at compile time — a typo on either side compiles fine and just silently never fires the turn banner. Worth a shared constant or union type if a third consumer shows up.
- **Bandit Captain has no visual distinction from standard bandits.** The renderer colors units by *owner*, not unit type (same pre-existing gap as wolves' `PackLeader`/`PackFollower`). `isBanditCaptain` exists as an `instanceof`-based predicate for the Stage 3 narrative's "Captain defeated" trigger only, not as an exported general-purpose type guard.
- **Stage 3's Wanderer enclosure is an approximation.** Spec 11 wants the Wanderer "surrounded by tents on three sides, one open direction toward Whirley," but board texture doesn't block movement in this engine (only real grid bounds/occupancy do — there's no "tent"/obstacle-unit concept). `wanderer_spawn` sits at a genuine grid corner instead, giving 2 open directions rather than 1.

## Notes from early debugging

- **Pre-existing broken WIP in `shared/game_world.ts`** (found uncommitted at the start of this work): re-introduced the multi-layer "colored hex background + ship" unit rendering that an earlier commit had simplified away via sprite tint. It did not typecheck (`unitSprites: Map<number,Tile>` storing a `Container`; `.coordinates` assigned on a `Container`). Fixed minimally: `Map<number, Container>`, dropped the invalid `.coordinates` assignment (position is driven by the tweened container x/y).
- **Pre-existing wrong import**: `main/game_world.ts` imported `UnitPosition` from `../core/world` (not exported there) — fixed to `../core/board`.
